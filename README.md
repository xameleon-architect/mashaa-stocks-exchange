# Mashaa: МойСклад → Tilda — синхронизация остатков

Версия 0.5 предназначена только для тестового контура.

## Что делает инструмент

- читает товары, модификации и остатки выбранного склада из JSON API МоегоСклада;
- рассчитывает `Доступно = Остаток − Резерв + Ожидание`;
- сопоставляет позиции по `externalCode` МоегоСклада и `External ID` Tilda;
- формирует аудит CSV и пакет CommerceML `import0_1.xml` + `offers0_1.xml`;
- по умолчанию работает только в `dry-run`;
- записывает остатки в Tilda только после явного подтверждения;
- показывает восемь этапов обмена и единый итоговый статус;
- сохраняет понятный текстовый лог, JSONL-события и состояние последнего запуска;
- различает факт передачи пакета и подтверждённый итог в каталоге.

Инструмент передаёт только минимальные данные изменяемого товара, связь модификации, характеристики и остаток. Изображения, описания, цены и заказы не передаются.

## Требования

- Windows 10/11;
- Python 3.11 или новее;
- доступ компьютера к `api.moysklad.ru` и `store.tilda.ru`;
- токен тестового МоегоСклада;
- реквизиты CommerceML тестовой Tilda.

## Установка

1. Распакуйте архив в отдельную папку без кириллицы, например `C:\Tools\mashaa-tilda-sync`.
2. Запустите `install.bat`.
3. Откройте созданный файл `.env`.
4. Заполните значения:

```env
MOYSKLAD_TOKEN=...
TILDA_CML_URL=https://store.tilda.ru/connectors/commerceml/
TILDA_CML_LOGIN=...
TILDA_CML_PASSWORD=...
```

Не присылайте `.env` в чат и не добавляйте его в Git.

## Первый безопасный запуск

Запустите `run-dry.bat`. Скрипт прочитает данные, рассчитает изменения и ничего не отправит в Tilda.

Пример результата:

```text
[4/8] Сопоставление и проверка данных
[OK] Сопоставлено 165 из 165 (100.0%)
[5/8] Расчёт изменений остатков
[OK] Найдено изменений: 1
[7/8] Передача пакета в Tilda
[WARN] Dry-run: отправка в Tilda не выполнялась
ИТОГ: DRY_RUN_READY
```

После запуска создаются:

- `output/audit-*.csv` — полный список изменений;
- `output/import-*.xml` — минимальный каталог изменяемых товаров;
- `output/offers-*.xml` — предложения и остатки;
- `output/summary-*.json` — итог конкретного запуска;
- `logs/access-YYYY-MM-DD.log` — человекочитаемый журнал запусков и этапов обмена;
- `logs/error-YYYY-MM-DD.log` — ошибки с полным очищенным Python traceback, `run_id` и этапом;
- `logs/events-YYYY-MM-DD.jsonl` — структурированная история этапов;
- `status/latest.json` — состояние последнего запуска.

## Первый тест записи

1. Измените остаток одной тестовой модификации в МоемСкладе.
2. Запустите `run-dry.bat` и проверьте, что найдено только ожидаемое изменение.
3. Запустите `run-apply-once.bat`.
4. Введите `APPLY-TEST-TILDA`.
5. Дождитесь статуса `SUBMITTED_UNVERIFIED`.
6. Проверьте остаток нужной модификации в каталоге Tilda вручную.

Статус `SUBMITTED_UNVERIFIED` означает, что Tilda подтвердила протокол CommerceML, но скрипт ещё не прочитал итоговый остаток обратно.

## Постоянная диагностика

`run-watch.bat` запускает диагностический dry-run раз в 60 секунд. Данные в Tilda не отправляются. Остановить процесс можно сочетанием `Ctrl+C`.

Постоянная запись `--watch --apply` заблокирована до реализации автоматической проверки результата Tilda. Для тестовой записи используйте только `run-apply-once.bat`.

## Итоговые статусы

- `DRY_RUN_READY` — изменения рассчитаны, отправки не было;
- `NO_CHANGES` — по текущему снимку изменений нет;
- `SUBMITTED_UNVERIFIED` — Tilda приняла пакет, но остаток автоматически не проверен;
- `SUCCESS_VERIFIED` — зарезервирован для будущего автоматического read-back;
- `BLOCKED` — обмен остановлен защитной проверкой до отправки;
- `FAILED` — обмен не завершён из-за известной ошибки;
- `OUTCOME_UNKNOWN` — передача началась, но результат неизвестен из-за обрыва связи.

## Коды ошибок

- `E_CONFIG` — ошибка `.env` или `config.json`;
- `E_MOYSKLAD_AUTH` — неверный токен МоегоСклада;
- `E_STORE_NOT_FOUND` — не найден выбранный склад;
- `E_MATCH_RATIO` — недостаточно сопоставленных позиций;
- `E_DUPLICATE_ID` — обнаружены дубли идентификаторов;
- `E_CML_AUTH` — ошибка авторизации CommerceML;
- `E_CML_UPLOAD` — ошибка загрузки пакета;
- `E_CML_IMPORT` — Tilda не завершила импорт;
- `E_LOCK` — другой экземпляр скрипта уже работает.

Каждая ошибка сопровождается причиной и рекомендуемым действием.

## Защитные механизмы

- режим записи требует отдельную команду и фразу подтверждения;
- совпадение менее 98% блокирует обмен;
- дубли идентификаторов блокируют обмен;
- отрицательное доступное количество передаётся как ноль;
- дробные количества по умолчанию запрещены;
- повторный процесс блокируется файлом `sync.lock`;
- токены, пароли и session cookie не записываются в отчёты;
- итоговые JSON и XML заменяются атомарно;
- каждый запуск получает уникальный `run_id` и ровно один итоговый статус;
- неподтверждённое локальное состояние по умолчанию не считается истиной.

## Настройка

Основные параметры находятся в `config.json`:

- `store_name` — точное название склада МоегоСклада;
- `watch_interval_seconds` — период, минимум 60 секунд;
- `minimum_match_ratio` — минимальная доля сопоставления;
- `clamp_negative_to_zero` — обнулять отрицательное доступное количество;
- `trust_local_state` — использовать ли локальное состояние; должно оставаться `false` до read-back;
- `status_dir` — каталог состояния последнего запуска.

## Диагностика

При ошибке передавайте разработчику три файла одного запуска:

- `output/summary-*.json`;
- `output/audit-*.csv`;
- `logs/access-YYYY-MM-DD.log`;
- `logs/error-YYYY-MM-DD.log`.

Файл `.env` передавать нельзя.

## Ограничение версии 0.5

Последовательность CommerceML: `checkauth → init → file import0_1.xml → file offers0_1.xml → import import0_1.xml → import offers0_1.xml`. Подтверждение этой последовательности не доказывает, что итоговый остаток уже прочитан из каталога Tilda. Поэтому успешная передача имеет статус `SUBMITTED_UNVERIFIED`, а постоянная автоматическая запись пока заблокирована.
